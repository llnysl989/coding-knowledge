# Git 基础与 223 知识库同步操作手册

## 1. 适用场景

本文档用于说明：

- Git 中工作区、提交、分支、远程分支分别是什么。
- `checkout`、`fetch`、`pull`、`merge`、`rebase`、`reset` 等命令有什么区别。
- 为什么 223 上的 `main` 会与 `origin/main` 分叉。
- 本地电脑修改并推送代码后，如何安全地更新 223 上的知识库仓库。
- 如何避免人工操作与每天 10 点的知识库同步任务互相影响。

知识库在 223 上的路径：

```text
/data/homework/multica-runtime-docker/runtime-data/ugc-data-knowledge
```

223 使用的 Git 版本较旧：

```text
git version 1.8.3.1
```

因此本文在 223 上统一使用兼容 Git 1.8.3.1 的命令，不使用 `git switch`、`git branch --show-current` 和 `git -C`。

---

## 2. Git 的四个重要位置

理解 Git 时，可以把代码分成四个位置：

```text
工作区  ->  暂存区  ->  本地提交历史  ->  GitLab 远程仓库
 edit       git add     git commit       git push
```

### 2.1 工作区

工作区就是磁盘上能够直接看到和编辑的文件。

例如：

```text
vault/projects/growth-data/tables/ugc.dws_user_tags_qsl_df.md
```

文件修改或删除后，变化首先只存在于工作区，还没有形成 Git 提交。

### 2.2 暂存区

执行 `git add` 后，指定变化进入暂存区，表示准备放入下一次提交。

```bash
git add path/to/file
```

暂存已跟踪文件的修改和删除：

```bash
git add -u
```

### 2.3 本地提交历史

执行 `git commit` 后，暂存区中的变化形成一个本地提交：

```bash
git commit -m 'chore: update knowledge files'
```

此时提交只存在于当前机器，还没有进入 GitLab。

### 2.4 GitLab 远程仓库

执行 `git push` 才会把本地提交发送到 GitLab：

```bash
git push origin <分支名>
```

`origin` 是远程仓库的本地别名，不是分支名称。

## 3. 分支、HEAD 和 origin/main

### 3.1 分支

分支可以理解为指向某个提交的可移动标签。

例如：

```text
main
automation/knowledge-sync-20260807-174809
chore/remove-obsolete-knowledge
```

查看本地和远程跟踪分支：

```bash
git branch -a
```

### 3.2 HEAD

`HEAD` 表示当前检出的提交，通常指向当前分支。

查看当前分支，兼容 223 的 Git 1.8.3.1：

```bash
git rev-parse --abbrev-ref HEAD
```

### 3.3 origin/main 不等于实时的 GitLab main

`origin/main` 是本地保存的“上次获取到的远程 main 快照”。它不会自动实时更新。

```text
GitLab main  --git fetch-->  本地 origin/main
```

只有执行 `git fetch` 后，本地 `origin/main` 才会刷新。

223 使用旧版 Git，建议显式更新远程跟踪分支：

```bash
GIT_SSH='/data/homework/knowledge-sync/bin/git-ssh-knowledge-sync.sh' \
git fetch origin \
  '+refs/heads/main:refs/remotes/origin/main'
```

不要只根据未执行 `fetch` 前的 `origin/main` 判断远程状态。

## 4. 常见状态字母

执行：

```bash
git status --short
```

常见结果：

| 状态 | 含义 |
|---|---|
| `M` | 文件被修改 |
| `D` | 文件被删除 |
| `A` | 新文件已加入暂存区 |
| `??` | 新文件未被 Git 跟踪 |

例如切换到 `main` 时出现：

```text
D vault/projects/growth-data/tables/ugc.dws_user_tags_qsl_df.md
```

表示该文件在当前工作区中已经删除，但删除尚未提交。Git 在切换分支时保留了能够安全携带的未提交变化，所以这些删除会跟随工作区切换到 `main`。

未提交变化不真正属于任何分支。只有提交后，它才进入当时所在分支的历史。

## 5. 常用命令的区别

### 5.1 git checkout

切换分支：

```bash
git checkout main
```

从指定提交创建新分支：

```bash
git checkout -b chore/example origin/main
```

恢复文件到当前提交中的版本：

```bash
git checkout -- path/to/file
```

最后一种操作会丢弃该文件未提交的变化，执行前必须确认。

### 5.2 git fetch

从 GitLab下载提交和分支信息，但不修改当前工作区，也不会自动合并。

```bash
git fetch origin
```

它通常是最安全的远程同步命令。

### 5.3 git merge --ff-only

只允许“快进”更新：当前分支必须是目标分支的祖先。

```bash
git merge --ff-only origin/main
```

如果双方各自存在独有提交，命令会拒绝执行：

```text
fatal: Not possible to fast-forward, aborting.
```

这不是程序损坏，而是安全保护：Git 不会替你自动生成合并提交，也不会覆盖任何一边的历史。

### 5.4 git pull

普通 `git pull` 可以近似理解为：

```text
git fetch + git merge
```

它会在获取远程提交后立即修改当前分支。当本地和远程分叉时，普通 `git pull` 可能创建一个额外的合并提交，因此不适合 223 上应当保持为远程镜像的 `main`。

如果只是个人开发机上的正常线性更新，可以使用：

```bash
git pull --ff-only origin main
```

在 223 的共享自动化仓库中，推荐把 `fetch` 和 `merge --ff-only` 拆开执行，便于检查每一步。

### 5.5 git rebase

`rebase` 会把当前分支的独有提交重新放到另一个分支最新提交之后。

```bash
git rebase origin/main
```

适合更新尚未共享的个人功能分支。它会改写提交 ID，不要随意对多人共同使用、已经推送的分支执行。

### 5.6 git reset --hard

强制把当前分支和工作区对齐到指定提交：

```bash
git reset --hard origin/main
```

它会丢弃当前分支的独有提交引用以及未提交修改，属于破坏性命令。执行前必须：

1. 检查 `git status`。
2. 用备份分支保留仍然需要的提交。
3. 明确确认后再执行。

### 5.7 git push

把本地分支推送到 GitLab：

```bash
git push -u origin chore/example
```

知识库流程不应直接从 223 推送 `main`，应推送独立分支后创建 MR。

### 5.8 Merge Request

MR 用于把源分支合并进目标分支：

```text
chore/example  ->  main
```

当前知识库自动化流程会：

1. 创建 `automation/knowledge-sync-*` 分支。
2. 提交并推送变更。
3. 使用 GitLab API 创建 MR。
4. 等待 MR 可合并。
5. 自动合并进 `main`。
6. 保留源分支。

## 6. 本次 main 分叉案例

### 6.1 当时的状态

执行日志显示：

```text
Your branch and 'origin/main' have diverged,
and have 1 and 2 different commits each, respectively.
fatal: Not possible to fast-forward, aborting.
```

进一步检查：

```text
< e807b71 (main) chore: remove obsolete knowledge files
> 904b473 (origin/main) Merge branch 'automation/knowledge-sync-20260807-174809' into 'main'
> 5a68ae4 chore(knowledge): sync assets for 2026-08-06
```

其中：

- `<` 表示只存在于本地 `main`。
- `>` 表示只存在于远程 `origin/main`。

### 6.2 分叉过程

可以简化为：

```text
共同旧提交
├── 本地 main: e807b71 删除旧知识文件
└── 远程 main: 5a68ae4 -> 904b473 自动同步并合并 MR
```

本地在 `main` 上直接提交删除；与此同时，GitLab 的 `main` 通过自动化 MR 增加了新提交。双方都不是对方的直接祖先，所以 `--ff-only` 无法更新。

### 6.3 为什么脚本失败是正确行为

脚本如果强行继续，可能产生以下问题：

- 自动生成难以追踪的合并提交。
- 把不应直接进入 `main` 的本地提交混入自动化流程。
- 出现冲突时错误覆盖知识文件。

因此脚本以 `exit_code=128` 停止，是安全保护，不是数据同步代码本身失败。

### 6.4 正确恢复方法

先把本地独有提交保存为功能分支：

```bash
git branch chore/remove-obsolete-knowledge e807b71
```

确认备份后，让本地 `main` 对齐远程：

```bash
git checkout main
git reset --hard origin/main
```

再把删除提交更新到最新远程历史之上：

```bash
git checkout chore/remove-obsolete-knowledge
git rebase origin/main
```

最后推送该分支并通过 MR 合并，不直接推送 `main`。

## 7. 推荐的完整日常流程

### 7.1 在本地电脑开发

开始修改前，先更新本地 `main`：

```bash
git checkout main
git pull --ff-only origin main
```

从最新 `main` 创建独立分支：

```bash
git checkout -b feature/<本次变更名称>
```

修改后检查、暂存并提交：

```bash
git status --short
git diff
git add -- <需要提交的路径>
git commit -m '<提交说明>'
```

推送功能分支：

```bash
git push -u origin feature/<本次变更名称>
```

在 GitLab 创建 MR，将功能分支合并到 `main`。

不要在本地直接向 `main` 提交后立刻推送，除非项目明确允许且没有 MR 流程。

### 7.2 MR 合并后更新 223

如果只是等待每天 10 点的知识库同步任务，可以不手动操作。定时任务启动时应更新本地 `main`。

如果需要立即更新 223，先确认没有定时同步任务正在执行：

```bash
ps -ef | grep '[d]aily_sync.py'
ps -ef | grep '[r]un_daily_sync.sh'
```

进入仓库：

```bash
cd /data/homework/multica-runtime-docker/runtime-data/ugc-data-knowledge
```

检查工作区和当前分支：

```bash
git status --short
git rev-parse --abbrev-ref HEAD
```

要求：

- `git status --short` 没有输出。
- 当前可以安全切换到 `main`。

更新本地远程快照：

```bash
GIT_SSH='/data/homework/knowledge-sync/bin/git-ssh-knowledge-sync.sh' \
git fetch origin \
  '+refs/heads/main:refs/remotes/origin/main'
```

切换并快进更新 `main`：

```bash
git checkout main
git merge --ff-only origin/main
```

验证本地和远程提交一致：

```bash
git rev-parse main
git rev-parse origin/main
```

两个提交 ID 应该相同。

### 结论：223 上是否直接执行 git pull

不建议在 223 的共享自动化仓库里直接执行不带参数的：

```bash
git pull
```

推荐固定使用：

```bash
git fetch origin '+refs/heads/main:refs/remotes/origin/main'
git merge --ff-only origin/main
```

这样可以把“下载远程变化”和“更新本地 main”分开；如果发生分叉，第二步会安全失败，不会自动制造合并提交。

生产环境的 `run_daily_sync.sh` 在任务开始前和 MR 合并后也应使用上述显式 refspec。若脚本仍然是 `git fetch origin main`，建议后续单独调整为本文命令；旧版 Git 可能只更新 `FETCH_HEAD`，不保证同步更新本地 `origin/main`。

## 8. 223 上必须遵守的规则

### 8.1 不直接在 main 提交

错误示例：

```bash
git checkout main
git add .
git commit -m '临时修改'
```

这会让本地 `main` 出现 GitLab 没有的提交，下一次定时同步可能再次分叉。

需要在 223 临时修改时，应从最新远程 `main` 创建分支：

```bash
git fetch origin '+refs/heads/main:refs/remotes/origin/main'
git checkout -b fix/<变更名称> origin/main
```

提交后推送该分支并创建 MR。

### 8.2 不在同步任务运行时手动更新仓库

自动化任务会切换分支、写入文件、提交和创建 MR。此时人工执行 `checkout`、`pull`、`reset` 可能破坏它的工作区。

### 8.3 看到工作区不干净时停止

如果下面命令有输出：

```bash
git status --short
```

不要直接 `pull`、`reset` 或切换分支。先判断修改属于：

- 正在运行的自动化任务。
- 人工未提交修改。
- 上次失败遗留的修改。

### 8.4 看到 diverged 时停止

使用下面命令查看双方独有提交：

```bash
git log --oneline --graph --decorate --left-right main...origin/main
```

不要直接使用 `reset --hard`、强制推送或随意合并。应先把有价值的本地提交保存到独立分支。

## 9. 常见问题处理

### 9.1 fatal: Not possible to fast-forward, aborting

含义：本地分支与目标分支已经分叉。

处理步骤：

```bash
git status --short
git log --oneline --graph --decorate --left-right main...origin/main
```

先识别本地独有提交是否需要保留，再决定创建备份分支或对齐远程。

### 9.2 工作区出现 D 文件

含义：受 Git 管理的文件在工作区中被删除。

检查删除内容：

```bash
git diff --name-status
git diff -- path/to/file
```

确认需要删除后，将其放到功能分支提交；不要在共享 `main` 直接提交。

### 9.3 当前位于 automation 分支

先检查工作区：

```bash
git status --short
```

如果干净，再更新并切回 `main`：

```bash
git fetch origin '+refs/heads/main:refs/remotes/origin/main'
git checkout main
git merge --ff-only origin/main
```

### 9.4 SSH 主机名无法解析

223 的仓库 `origin` 使用 Docker 内可识别的 SSH 别名，宿主机通过包装脚本转换真实主机名。因此宿主机 Git 命令需要：

```bash
GIT_SSH='/data/homework/knowledge-sync/bin/git-ssh-knowledge-sync.sh' \
git <子命令>
```

不要为了宿主机操作而修改共享仓库的 `origin`，否则可能导致 Docker 运行时无法拉取。

## 11. 最终约定

1. 本地开发使用独立分支，通过 MR 合并到 `main`。
2. 223 的本地 `main` 只作为 GitLab `main` 的镜像，不直接提交。
3. 223 更新代码使用 `fetch + merge --ff-only`，不使用普通 `git pull`。
4. 每日同步使用 `automation/knowledge-sync-*` 独立分支并自动创建、合并 MR。
5. 自动同步运行期间不进行人工 Git 操作。
6. 工作区不干净或分支分叉时停止操作，先检查和保留有价值提交。
7. `reset --hard`、强制推送和强制删除分支必须经过明确确认。
